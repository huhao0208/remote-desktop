## 0. 先纠正一个前提

### "全端支持"要拆成两个角色

远程桌面有两种角色，平台能力差异极大：

| 平台 | **控制端**（看画面、发输入） | **被控端**（提供画面、注入输入） |
|---|---|---|
| Windows | ✅ 完全 | ✅ 完全 |
| macOS | ✅ 完全 | ✅ 完全（需 ScreenCaptureKit 权限） |
| Linux | ✅ 完全 | ✅ 完全（PipeWire/X11） |
| Android | ✅ 完全 | ⚠️ 需 MediaProjection 每次授权，后台受限 |
| iOS | ✅ 完全 | ❌ **基本不可能**（ReplayKit 只能录制本 App，无系统级屏幕采集 + 注入） |

**关键事实**：iOS 做被控端在系统层面就不成立。所以"全端"的准确表述是：

- **控制端**：五端全支持 ← 这才是你要做的
- **被控端**：Win / macOS / Linux 为主，Android 可选，**iOS 不做**

如果你的需求是"iOS 手机看电脑"，那完全可行；如果是"iOS 手机被控"，建议直接放弃。

## 1. "性能最佳"在远控语境下等于什么

不要用 UI 框架的 benchmark 选型——那是错的评价体系。远控的真实指标：

| # | 指标 | 目标值 | 说明 |
|---|---|---|---|
| 1 | **端到端延迟** | 局域网 < 50ms，跨网 < 100ms | 鼠标动 → 画面反馈，这是体感第一指标 |
| 2 | 帧率稳定度 | 抖帧率 < 5%（30fps 基准） | 平均 60fps 但卡顿，体验比稳定 30 差 |
| 3 | 首帧时间 | < 500ms | 点击设备到出画面 |
| 4 | CPU 占用 | 1080p60 解码 < 25% | 笔记本续航/风扇 |
| 5 | 内存 | 控制端 < 500MB | 多开窗口时 ×N |
| 6 | 包体积 | 移动端 < 50MB | 下载转化率 |

### 延迟拆解（决定优化优先级）

```
鼠标事件发生
  ↓ 2-5ms      UI 事件处理（框架影响区）
  ↓ 1-2ms      打包
  ↓ 网络 RTT   ← 最大变量（局域网 1-3ms，跨网 20-80ms）
  ↓ 编码 5-15ms
  ↓ 传输队列   ← TCP 队头阻塞会让这里变成 50-500ms
  ↓ 解码 3-10ms
  ↓ 渲染 5-16ms（受 vsync 影响）
画面更新
```

**结论**：
- **UI 框架只影响第一段（2-5ms），占总延迟不到 5%**
- **传输协议影响传输队列，能差 10 倍**
- **编码影响带宽与 CPU，是第二大头**

所以：**换 UI 框架的收益，远小于把 TCP 换成 UDP。**

## 2. 五端平台能力矩阵

这是选型的硬约束，不是偏好问题。

### 2.1 采集（被控端）

| 平台 | API | 备注 |
|---|---|---|
| Win | DXGI Desktop Duplication / Windows.Graphics.Capture | 前者零拷贝到 D3D11 纹理，延迟最低 |
| macOS | ScreenCaptureKit（12.3+） | 输出 IOSurface，可直接进 VideoToolbox |
| Linux | PipeWire（Wayland）/ XShm（X11） | Wayland 是趋势，XShm 在退化 |
| Android | MediaProjection | 每次会话需用户授权，无法静默 |
| iOS | ❌ | ReplayKit 仅限本 App 内录制 |

### 2.2 硬解

| 平台 | API | 输出格式 | 零拷贝到 GPU |
|---|---|---|---|
| Win | Media Foundation / D3D11VA | D3D11 Texture | ✅ |
| macOS | VideoToolbox | CVPixelBuffer（IOSurface 背衬） | ✅ |
| Linux | VA-API / NVDEC | DMA-BUF | ✅ |
| Android | MediaCodec | Surface / ImageReader | ✅（Surface 输出） |
| iOS | VideoToolbox | CVPixelBuffer | ✅ |

### 2.3 Web 技术栈的解码能力（关键）

| 容器 | 内核 | WebCodecs | GPU 零拷贝路径 |
|---|---|---|---|
| Electron (Win) | Chromium | ✅ 完整 | WebGL `texImage2D(VideoFrame)` |
| Electron (macOS) | Chromium | ✅ 完整 | 同上 |
| Electron (Linux) | Chromium（自带） | ✅ 完整 | 同上 |
| Tauri (Win) | WebView2 | ✅ | 同上 |
| Tauri (macOS) | WKWebView | ✅ Safari 16.4+ | 同上 |
| **Tauri (Linux)** | **WebKitGTK** | **⚠️ 支持不全** | **GPU 路径弱** |
| Capacitor (Android) | Android WebView | ✅ Chrome 94+ | 可用但版本碎片 |
| **Capacitor (iOS)** | **WKWebView** | **⚠️ Safari 26 才完整；16.4–18.7 仅 VideoDecoder/Encoder** | 旧版不可依赖 |

> 来源：caniwebview.com WebCodecs 矩阵、openpwa.net 兼容性表（2026 查证）

**这张表直接排除了两个选项**：
1. **Tauri 在 Linux** —— WebKitGTK 的 WebCodecs 与 GPU 路径是硬伤
2. **Capacitor 在 iOS 旧版** —— Safari < 26 的 WebCodecs 不完整，必须原生兜底

## 3. 六个候选方案对比

| 方案 | 五端覆盖 | 性能上限 | 代码复用 | 包体积 | 开发速度 | 关键风险 |
|---|---|---|---|---|---|---|
| **A. Electron + Capacitor**（当前） | 5/5 | 中高 | 95% | 大（150M+ / 移动 30M） | ★★★★★ | 移动端 WebView 解码不可控 |
| **B. Tauri 2.0 全端** | 5/5 | 中 | 90% | 小（<10M） | ★★★☆☆ | **Linux WebKitGTK 弱**；移动 WebView 同样不可控 |
| **C. Flutter 全端** | 5/5 | 高 | 85%（UI） | 中（20M） | ★★★☆☆ | 视频需自写 Texture 直通；失去 Web 生态 |
| **D. Qt 6 全端** | 5/5 | 最高 | 65% | 中 | ★★☆☆☆ | 授权（LGPL/商业）；移动端体验一般 |
| **E. 原生五套** | 5/5 | 最高 | 0% | 小 | ★☆☆☆☆ | 维护成本 ×5 |
| **F. 混合：TS UI + Rust 媒体核心 + 原生渲染插件** | 5/5 | 高 | 80% | 中 | ★★★☆☆ | 工程复杂度最高 |

### 逐项说明

**A. Electron + Capacitor（当前路线）**
- 优点：五端一套 HTML/Vue；桌面三端 Chromium 一致；Linux 自带 Chromium **反而是优势**；你已有代码
- 缺点：桌面包体 150M+、内存 200-400MB；移动 WebView 解码需原生插件补齐
- 性能上限：桌面可达标（WebCodecs 硬解 + WebGL），移动需插件

**B. Tauri 2.0 全端**
- 优点：包体 600K-5M、内存省 60%、Rust 后端可直调原生
- 缺点：**Linux 用 WebKitGTK，WebCodecs 支持不全 + GPU 路径弱** → 五端性能不一致；移动端 WKWebView/Android WebView 解码同样不可控；换框架的收益（包体/内存）对远控场景**不产生延迟改善**
- 判断：**为省包体牺牲 Linux 性能，不划算**

**C. Flutter 全端**
- 优点：五端 UI 一致（自绘引擎）；渲染性能一致
- 缺点：低延迟视频要 `Texture` + platform channel + 原生解码器，三个平台各写一遍，工作量 ≈ 写 Capacitor 插件；失去 `xterm.js`、`VideoDecoder` 等现成库
- 判断：**如果 UI 复杂度高、且愿意投 3-4 周做视频直通，是不错的选择**

**D. Qt 6**
- 优点：C++ 原生性能，`QVideoSink` 直通，五端支持
- 缺点：LGPL 商业风险、移动端体验落后、开发速度最慢
- 判断：个人项目不推荐

**E. 原生五套**
- 性能天花板，但五人团队工作量。**个人项目不可行**

**F. 混合架构**
```
┌─────────────────────────────────────┐
│ UI 层：TypeScript（Vue/React）       │  ← 五端复用
├─────────────────────────────────────┤
│ 媒体核心：Rust（cargo 交叉编译五端）  │  ← 写一次
│   ├ 采集：平台条件编译               │
│   ├ 编解码：硬解优先 + openh264 兜底  │
│   ├ 传输：quinn(QUIC) / webrtc-rs    │
│   └ 输入注入：平台条件编译           │
├─────────────────────────────────────┤
│ 渲染桥：各端原生 Surface/Texture     │  ← 三套薄封装
└─────────────────────────────────────┘
```
- 优点：性能最好且一致，核心逻辑只写一次
- 缺点：需要 Rust 能力，构建链复杂（NDK/Xcode/交叉编译）

## 4. 推荐方案：分端差异化，不追求"一套框架包打天下"

### 4.1 结论

```
桌面三端：Electron（保留）+ WebCodecs + WebGL 纹理直通
移动两端：Capacitor + 原生解码插件（Surface / CVPixelBuffer 直通）
共享：    同一套 HTML/Vue UI + 同一套 TS 信令协议
```

~~**不用 Tauri，不用 Flutter，不换框架。**~~

> ⚠️ **以上结论已作废**（见文档顶部警告）。实际决策：**换 Flutter**，见 `客户端框架重选型-Flutter.md`。

### 4.2 理由（按权重）

| # | 理由 | 权重 |
|---|---|---|
| 1 | **性能瓶颈不在框架**：延迟 5% 来自 UI，10 倍差异在传输协议 | ★★★★★ |
| 2 | **Linux 是 Electron 的隐藏优势**：自带 Chromium，不依赖系统 WebKitGTK | ★★★★☆ |
| 3 | **已有代码 95% 可复用**：UI + 信令 + 状态机 | ★★★★☆ |
| 4 | **移动端问题用插件解决更精准**：只下沉解码渲染这一层，不动 UI | ★★★★☆ |
| 5 | 团队技术栈匹配（Web），无 Rust/Flutter 学习成本 | ★★★☆☆ |
| 6 | 包体大是缺点，但桌面场景不痛（移动端 Capacitor 只 30M） | ★★☆☆☆ |

### 4.3 各端的具体渲染路径

#### 桌面（Electron）—— 目标 1080p60 延迟 < 30ms

```
H.264 码流
  ↓ VideoDecoder（WebCodecs，硬解优先）
VideoFrame
  ↓ texImage2D（零拷贝，直接吃 VideoFrame）
WebGL Texture
  ↓ 单 pass 渲染
Canvas（desynchronized: true）
```

关键点：
- ❌ **不要用 canvas 2D `drawImage`** —— 有 CPU 拷贝，1080p60 会吃掉 30% CPU
- ✅ `gl.texImage2D(..., videoFrame)` 直接上传，Chromium 内部走 GPU
- ✅ canvas context 用 `{ desynchronized: true }` 降低合成延迟
- ✅ 解码队列深度控制在 2-3 帧，超了丢帧不排队
- ✅ `VideoDecoder.isConfigSupported()` 探测，不支持回落软解

#### Android（Capacitor 插件）—— 目标 1080p60 延迟 < 50ms

```
H.264 码流（JS → 原生 JNI）
  ↓ MediaCodec（配置 output surface）
SurfaceTexture
  ↓ GLSurfaceView / TextureView
屏幕上屏
```

关键点：
- `MediaCodec.configure(format, surface, ...)` 直接输出到 Surface，**不经过 Bitmap**
- 用 `SurfaceTexture` + `GLSurfaceView` 或 `TextureView`
- **不要用 `ImageReader` + Bitmap**（多一次 CPU 拷贝）

#### iOS（Capacitor 插件）—— 目标 1080p60 延迟 < 50ms

```
H.264 码流（JS → 原生 Swift）
  ↓ VTDecompressionSession（硬解）
CVPixelBuffer（IOSurface 背衬）
  ↓ CVMetalTextureCache
MTLTexture
  ↓ MTKView 渲染
上屏
```

关键点：
- `CVMetalTextureCacheCreateTextureFromImage` 实现零拷贝
- `MTKView` 的 `preferredFramesPerSecond` 设 60，`enableSetNeedsDisplay = false`（持续刷新）
- 避免 `CIImage`/`UIImage` 中转

### 4.4 媒体核心的代码组织（为将来切 Rust 留口）

```
client-shared/
├── protocol/          ← TS：WS 消息定义、编解码（五端共用）
├── renderer/
│   ├── web/           ← WebCodecs + WebGL（桌面 + Android WebView 兜底）
│   └── native-bridge.ts  ← 统一接口，桌面走 Web，移动走原生插件
└── input/             ← 输入事件采集（归一化坐标，五端共用）
```

`native-bridge.ts` 定义统一接口：
```ts
interface VideoRenderer {
  init(canvas: HTMLCanvasElement | null, config: DecoderConfig): Promise<void>;
  push(chunk: EncodedChunk): void;
  destroy(): void;
  readonly stats: { decodeMs: number; renderMs: number; dropped: number };
}
```
桌面注入 `WebCodecsRenderer`，移动注入 `NativeRenderer`（走 Capacitor 插件）。**UI 层零感知。**

这样将来如果真的需要 Rust 核心，只需替换 `NativeRenderer` 的实现，UI 完全不动。

## 5. 迁移路径（三阶段，按 ROI 排序）

### 阶段 0（1 周）：先把桌面做到位
```
1. 传输：WS → UDP（自研包格式，NACK + 丢帧策略）   ← 收益最大
2. 编码：JPEG → H.264（硬编）
3. 渲染：canvas drawImage → WebCodecs + WebGL
4. 验收：局域网 1080p60 < 30ms，CPU < 25%
```
> 这三项做完，桌面端体验已经接近商业产品。**换框架也不会有额外收益。**

### 阶段 1（2-3 周）：移动端原生解码插件
```
1. 写 Capacitor 插件骨架（Android Kotlin / iOS Swift）
2. Android：MediaCodec → SurfaceTexture → GLSurfaceView
3. iOS：VTDecompressionSession → CVMetalTextureCache → MTKView
4. UI 复用现有 www/index.html，只换 renderer 实现
5. 验收：1080p30 < 50ms，CPU < 30%，iOS 15+ 可用
```

### 阶段 2（可选，视需要）：统一媒体核心
```
仅当出现以下情况才做：
- 五端逻辑重复严重，维护成本 > 重构成本
- 需要 AV1 / 更复杂的拥塞控制
- 团队有 Rust 能力
做法：Rust 写 media-core，五端通过 FFI 调用，UI 不动
```

## 6. 如果优先级不同，怎么选

| 你的优先级 | 推荐方案 | 理由 |
|---|---|---|
| **最快可用、性能达标** | **A（Electron + Capacitor + 原生插件）** | 代码复用 95%，性能瓶颈不在框架 |
| 包体/内存优先（如做产品分发） | B（Tauri）但 **Linux 单独处理** | Linux 用 Electron 或原生，其余 Tauri |
| UI 五端绝对一致 | C（Flutter）+ 自写 Texture 直通 | 需投 3-4 周做视频层 |
| 极致延迟（对标 Parsec） | F（Rust 核心 + 原生渲染） | 成本最高，需 Rust 能力 |
| 商业产品、有团队 | E（原生五套）或 D（Qt） | 人力换性能 |

## 7. 不管选哪个方案，这些必须做

这些是**跨方案共性**的，先做这些比换框架有用：

| # | 项 | 收益 |
|---|---|---|
| 1 | **传输走 UDP**（非 TCP） | 延迟 -60%，弱网不掉帧 |
| 2 | **硬解优先**（`isConfigSupported` 探测 + 软解兜底） | CPU -50% |
| 3 | **零拷贝渲染**（纹理直通，不经过 CPU 内存） | 延迟 -15ms，CPU -30% |
| 4 | **解码队列深度限制**（2-3 帧，超了丢） | 防延迟累积 |
| 5 | **关键帧请求机制**（丢包后主动要 IDR） | 恢复时间从 2s → 100ms |
| 6 | **输入事件合并**（鼠标移动 60Hz 采样 + 高精度时间戳） | 输入延迟 -10ms |
| 7 | **渲染与 vsync 对齐**（避免撕裂和额外缓冲） | 抖动 -50% |
| 8 | **码率自适应**（按 RTT/丢包反馈调） | 弱网可用性 |

---

## 8. 一句话总结

> **别换框架，先换传输。** 你现在用 Electron 但走 TCP + JPEG，换到任何框架都救不了延迟；把 UDP + H.264 + WebCodecs 做完，Electron 在桌面三端已经够用。移动端用 Capacitor 插件把解码下沉到原生 Surface/Texture，UI 不用重写。
