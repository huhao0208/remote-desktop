# 远控功能复刻基线（对标 UU 远程 4.48.1）

> 基准材料：`docs/reverse/UU远程-{功能逆向分析报告,远控核心全量技术分析,远程功能与UI设计还原}.md`
> 材料性质：**结构级逆向**（Mach-O 元数据、字符串层、protobuf 消息名、资源名、plist），非源码还原。
> 本文用途：把官方能力面转成本项目的**逐项验收标准**，任何远控功能实现前先在此登记状态。
> 更新规则：改动落地后同步「现状」列，不留口头结论。

---

## 0. 复刻原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **对外行为一比一，对内实现自选** | 文案、交互顺序、状态机、提示分级对齐官方；引擎用 aiortc/Python 而非 libstreamer |
| 2 | **协议只在 `docs/media-protocol.md` 内演进** | 新消息优先复用已有 `p` 字段；服务端 `srv2/server.py` 保持零改动（WS 透传） |
| 3 | **每项都要有降级路径** | 官方按显卡/机型降级，本项目按「能力探测 + 协商失败→降一档」处理，不静默失败 |
| 4 | **不做项要写明理由** | 见 §5，避免反复讨论同一件事 |

**P1 附注：macOS 防窥怎么解决的（实测，2026-11-21 本机 2048×1280）**

先被推翻的两个假设：

| 手段 | 结果 |
|---|---|
| `pmset displaysleepnow` 后 `mss` | `monitors` 变成 `0×0`，抓不到任何画面 |
| 熄屏后 `screencapture` | `could not create image from display` |
| 普通全屏遮罩窗（几何/映射均正常） | 会被自己的采集一起录进去 → 控制端全黑 |

真正的解法是让遮罩窗**不进采集合成**：`NSWindow.sharingType = NSWindowSharingNone(0)`，
用 ctypes 调 objc runtime 设置，零新依赖。同一窗口同一层级只切这个属性：

| `sharingType` | 合成图里 `#101010` 遮罩像素占比 | 中心像素 |
|---|---|---|
| 1（默认） | **91.7%** | `(16,16,16)` 遮罩 |
| 0 | **0.2%** | 桌面内容 |

用仓库真实模块端到端对照：不加 `--exclude-capture` 时合成图 79.8% 是遮罩，加了只剩 8.3%
（等于桌面暗部基线 8.4%）。mss 用的就是这条 `CGWindowListCreateImage` 路径，所以主采集通路
生效；路线 B（pyobjc + 换采集路径）不需要了。

顺带修掉一个坑：macOS/Tk 9 上 `attributes("-topmost", True)` **不改 NSWindow 层级**（实测恒为 0），
用户点一下自己的窗口就把遮罩盖住了 → 显式 `setLevel:25`（盖住普通窗口/Dock/菜单栏，不碰
屏保与锁屏层 1000+）。

失败时**不降级放行**：找不到 NSWindow 或 `sharingType` 回读不为 0 → 子进程退出码 4，
父进程返回 `{ok:false, err:...}`，绝不给一个「看起来开了、控制端全黑」的假开关。
macOS 的 `screenoff` 档继续拒绝（熄屏必断流）。

**仍未覆盖**：macOS 15 的 `screencapture` 已链接 ScreenCaptureKit，实测 SCK 对 `sharingType=0`
的窗口返回纯黑图而不是剔除它——所以「mss 被 TCC 挡住 → `screencapture` 兜底」这条路上遮罩可能
表现为黑块。主路径不受影响，待真机确认。

**画质实测（JPEG 通路真链路）**：`width:0`（原画）→ ack `width:0`；
`2560/30` → ack 原样；`854/144` → ack `fps:144`；越界 `99999/999` → 钳到 `3840/144`。
JPEG 通路 ack **不带** `bitrate`（协议 §4 允许缺省），避免 UI 显示误导性的「0kbps」。

- 2026-11-21：**B 阶段收尾：控制端麦克风（语音喊话）**（协议 media-protocol §6）。
  这一项拖到最后做，因为它要动 WebRTC 协商——最贵的一次改动。
  **定位为单向**（控制端 → 被控端扬声器），不做双向通话：同一条 PC 上两条音频 m-line
  会变成实时音频工程（AEC / 双讲 / 抢占），不是远控该背的复杂度。控制端采集强制开
  `echoCancellation + noiseSuppression`——它自己的扬声器正在放被控端的声音，不开必啸叫。
  **核心设计（零重协商）**：`createOffer` 阶段就把 audio m-line 建成 `sendrecv` 但不挂轨，
  开麦时只 `sender.replaceTrack(localMic)`。为什么不能开麦才 re-offer：Agent 的
  `handle_offer` 对同 peer 是「先关旧会话再重建」，一触发就会连画面一起重建、黑屏闪一下。
  空 `sendrecv` 不产生 RTP，带宽代价为 0。
  **隐私红线**：被控端**默认不放音**（`_Peer.muted = True`），必须收到 `mic{enable:true}`
  才出声；`RemoteAudioSink.gate` 负责在未开启时**消费帧但不出声**——不消费会让 aiortc
  的接收缓冲堆积，用户真开麦时听到的是几秒前的旧声音。
  **状态唯一真相源**：按钮亮不亮由 `mic.state` 回执决定，不由点击决定（`MicSwitch`），
  3 秒无回执弹回 OFF。这条防的就是「按钮亮着但没声音」。
  **补了三平台权限**（原来全缺，不补则真机必然失败）：macOS `NSMicrophoneUsageDescription`
  + 沙箱 `com.apple.security.device.audio-input`（缺了 getUserMedia 一律失败且**不弹授权框**，
  表现成「点了没反应」）、iOS `NSMicrophoneUsageDescription`、Android `RECORD_AUDIO`。
  **验证**：`flutter analyze` 干净；Flutter **438 项单测通过**（+13 麦克风状态机、
  +13 三个面板 widget 测试，另修 2 处测试自身期望值写错）；Agent **PASS 20 / FAIL 0**
  （+5 放音，其中「背压丢最旧」「欠载补静音」「垃圾帧不抛」是关键行为）；
  两端协议字段一致性用脚本核对通过（`mic` / `mic.state` / `enable` / `ok` / `on` / `err` 全对齐）。
  **未验证**：真机端到端出声（本机缺 `aiortc`/`sounddevice`，只能验降级路径）；
  真实 `av.AudioFrame` 的格式转换（`fltp`→`s16` 那条路没有样本帧）；
  「开麦不触发 rtc.offer」只做了代码层保证，没抓到包。
